# hentrOS

[English](README.md) | **Русский** | [中文](README.zh.md)

Крошечная хобби-операционная система с графическим рабочим столом в стиле
Windows, загружаемая через собственный UEFI-загрузчик. Написана с нуля на
freestanding C — никакого заимствованного кода ОС, никакого внешнего EFI SDK.

Это учебная демонстрация хобби-ОС, а не production или ОС общего
назначения. У неё нет драйвера файловой системы, модели процессов и сети.

## Что здесь есть

hentrOS — это единое UEFI-приложение (`BOOTX64.EFI`) — оно никогда не
вызывает `ExitBootServices`, поэтому отдельной стадии ядра нет. Оно
общается с прошивкой напрямую через небольшое, написанное вручную
подмножество UEFI API (`boot/efi.h`, без зависимости от gnu-efi/edk2):

- `boot/boot.c` — выбирает видеорежим через Graphics Output Protocol,
  рисует загрузочное меню, а затем запускает весь рабочий стол:
  градиентные обои, панель задач с кнопкой Пуск и живыми часами
  (`EFI_RUNTIME_SERVICES.GetTime`), перетаскиваемое окно с кнопкой
  закрытия и меню Пуск.
- `kernel/gfx.c`, `kernel/font.c` — небольшой программный растеризатор
  (прямоугольники, линии, градиенты, собственный битмап-шрифт 5x7),
  рисующий во внеэкранный буфер, плюс `gfx_present()`, который
  копирует его в реальный framebuffer одним блоком каждый кадр.
  Отрисовка за пределами экрана с последующим атомарным выводом — это
  то, что избавляет экран от мерцания и разрывов: рисование фигур
  напрямую в framebuffer, который дисплей одновременно сканирует,
  вызывает заметные разрывы кадра, тем сильнее, чем медленнее рисует
  машина.
- `kernel/logo.c` — стилизованная, процедурно нарисованная реконструкция
  оригинального рисованного маркером жёлтого логотипа проекта
  (штрихованный центр с восемью закручивающимися лепестками), построенная
  на целочисленной спиральной математике (без libm).

**Ввод** идёт через собственные протоколы UEFI, а не через прямой доступ
к железу: `EFI_SIMPLE_POINTER_PROTOCOL` (с откатом на
`EFI_ABSOLUTE_POINTER_PROTOCOL`) для мыши и `EFI_SIMPLE_TEXT_INPUT_PROTOCOL`
для клавиатуры. Это важно, потому что собственный стек драйверов UEFI
понимает USB HID-устройства — почти повсеместные на современном железе —
тогда как самодельный драйвер порта PS/2 вообще не увидел бы USB-мышь
или клавиатуру после того, как загрузочная прошивка передала управление.
Стрелки + Enter/Пробел всегда работают как резервный клавиатурный ввод
для всего рабочего стола на случай, если указывающее устройство не найдено.

Разные платы предоставляют указывающие устройства очень по-разному —
некоторые заканчивают USB-перечисление только через пару секунд после
включения, некоторые публикуют больше одного экземпляра указателя
(тачпад и USB-мышь одновременно), некоторые предоставляют только
абсолютный вариант. `desktop_loop()` в `boot/boot.c` справляется с этим
так: принудительно подключает всё дерево драйверов
(`connect_all_controllers()`, то же самое, что делает `connect -r` в
UEFI Shell, поскольку некоторые платы привязывают USB HID-драйверы
только по требованию), перечисляет *каждый* хендл для обоих протоколов
указателя вместо того, чтобы брать первый попавшийся из `LocateProtocol`,
повторяет это сканирование несколько секунд при старте, и периодически
пересканирует во время работы на случай горячего подключения или
позднего завершения перечисления устройства.

Если мышь всё ещё не двигается после этого, скорее всего дело в настройке
BIOS/UEFI, а не в том, что может исправить ОС: проверьте и **отключите
"Fast Boot"**, убедитесь, что **"Legacy USB Support"** /
**"USB Configuration"** установлено в полный/включённый режим, а не
"boot only" или отключено, и что **"XHCI Hand-off"** включён. Некоторые
платы пропускают полную инициализацию USB перед загрузкой ОС специально
для ускорения загрузки, из-за чего *любая* ОС (не только эта) не видит
мышь до гораздо более позднего момента обычной последовательности
загрузки. Резервный ввод с клавиатуры на экране (стрелки + Enter)
работает независимо от всего этого.

### Собственный драйвер мыши xHCI, написанный с нуля

Собственные протоколы указателя UEFI оказались ненадёжны на некоторых
реальных платах (экземпляр `EFI_ABSOLUTE_POINTER_PROTOCOL`, который
сообщает, что найден, но ни разу не возвращает реальное движение).
Теперь в `boot/boot.c` есть оригинальный драйвер xHCI (хост-контроллера
USB 3), написанный с нуля, а не позаимствованный из другого проекта,
который полностью обходит USB-стек UEFI для мыши:

1. Находит контроллер xHCI через `EFI_PCI_IO_PROTOCOL` (класс PCI
   0x0C/0x03, prog-if 0x30), включает декодирование памяти PCI и
   bus mastering, и считывает его 64-битный MMIO BAR. Видно как
   `XHCI: FOUND`.
2. Сбрасывает и инициализирует контроллер: останавливает его, выполняет
   сброс хост-контроллера, программирует Device Context Base Address
   Array, настраивает Command Ring и опрашиваемый Event Ring, и снова
   запускает его. Видно как `XHCIINIT: OK`. Взятие контроллера под
   свой контроль таким образом сбрасывает всё, что было настроено
   собственным USB-стеком прошивки, поэтому поддержка
   `EFI_ABSOLUTE_POINTER_PROTOCOL` в этот момент исчезает — это
   ожидаемо, поскольку этот драйвер её заменяет.
3. Сканирует каждый порт корневого хаба на предмет подключённого
   устройства, при необходимости выполняя Port Reset (работает как для
   USB2, так и для USB3 портов на xHCI).
4. Включает слот устройства, адресует его (`Address Device`) и
   получает его дескриптор конфигурации через дефолтную control
   конечную точку, чтобы найти interrupt IN конечную точку —
   предпочитая ту, что находится внутри интерфейса HID boot-protocol
   мыши, но принимая любую interrupt IN конечную точку как запасной
   вариант. Устанавливает конфигурацию и для HID-интерфейсов
   переключается в Boot Protocol.
5. Выполняет `Configure Endpoint` для этой interrupt конечной точки и
   держит в полёте один Normal TRB, декодируя каждый завершённый
   HID boot-mouse отчёт (кнопки, знаковые dx/dy) напрямую — без
   участия протокола указателя UEFI. Видно как `XHCIMOUSE: ACTIVE` с
   портом/слотом/конечной точкой, к которым он привязался, и
   `XHCISTATE`, показывающим собственное состояние Slot/Endpoint
   контроллера (Configured/Running, когда всё живо).

Это было проверено end-to-end в QEMU (`qemu-xhci` + `usb-mouse`):
сканирование портов, включение слота, адресация, разбор дескрипторов,
конфигурация и настройка конечной точки — всё успешно проходит, и
собственное состояние контроллера после этого читается как
Slot Configured / Endpoint Running именно так, как должно быть.
Подтвердить, что *живые HID-отчёты* проходят весь путь насквозь в
автоматизированном headless-тесте QEMU, не удалось из-за
маршрутизации ввода самого QEMU (там есть три конкурирующих
виртуальных указывающих устройства — PS/2, абсолютная "vmmouse" и
USB HID-мышь, и ни `mouse_move` монитора, ни `input-send-event` QMP,
ни события указателя VNC не удалось однозначно привязать именно к
USB-устройству в этом окружении) — это не похоже на баг в самом
драйвере. На реальном железе физическая мышь всего одна, так что этой
неоднозначности нет — если она всё равно не двигается, диагностика на
экране (`XHCIMOUSE`, `XHCISTATE`, `XHCIEVT`) покажет ровно, как далеко
зашла инициализация — это самый быстрый способ понять, чем отличается
конкретная плата.

## Командная строка

Небольшое окно-терминал: щёлкните по иконке **CMD** на рабочем столе
или **Пуск -> Command Line**, чтобы открыть его, либо **EXIT**/крестик
закрытия, чтобы закрыть. Пока оно открыто, у него собственный фокус
клавиатуры (чтобы набор текста не двигал заодно курсор мыши и не
вызывал клики по тому, что находится под ним), есть буфер прокрутки и
несколько встроенных команд:

| Команда       | Что делает |
|---------------|------|
| `HELP`        | вывести список встроенных команд |
| `ABOUT`       | о hentrOS |
| `VER`         | показать версию |
| `TIME` / `DATE` | текущее время/дата через `EFI_RUNTIME_SERVICES.GetTime` |
| `ECHO текст`  | вывести текст обратно |
| `CLS`         | очистить экран |
| `REBOOT`      | перезагрузить машину |
| `EXIT`        | закрыть окно |

За этим не стоит настоящей файловой системы или модели процессов — в
духе остальной части этой игрушечной ОС, это фиксированный набор
встроенных команд, а не полноценный шелл, запускающий программы.
Самодельный битмап-шрифт 5x7 покрывает только `0-9`, `A-Z` и несколько
знаков пунктуации (`: . , - ! '`), поэтому вывод команд ограничивается
этим набором, а не символами вроде `< > _ \ [ ]`.

## Загрузочное меню: Live или Установка

Загрузчик всегда показывает меню с двумя вариантами, прежде чем что-либо
сделать с диском:

- **[1] Live-режим** — запускает hentrOS прямо из RAM, используя только
  носитель, с которого была выполнена загрузка. Ничего ни на одном
  диске не записывается.
- **[2] Установка** — использует протокол UEFI Simple File System, чтобы
  найти другой дисковый том, и копирует `BOOTX64.EFI` на него в новую
  директорию `\EFI\HENTROS\`. Она никогда не трогает `\EFI\BOOT\` или
  любой другой существующий файл, так что установленная на этом диске
  Windows/Linux остаётся полностью нетронутой — hentrOS просто
  становится дополнительным пунктом, который можно выбрать в
  одноразовом загрузочном меню прошивки (например, F12/Esc при
  включении). После копирования она сразу же загружается в саму
  hentrOS, чтобы можно было тут же её попробовать.

## Готовый ISO

[`hentros.iso`](hentros.iso) в корне репозитория — это готовый,
загружаемый образ диска, никакого инструментария не нужно, чтобы его
попробовать. Это стандартный только-UEFI El Torito ISO (маленький
раздел EFI System Partition в FAT12, встроенный в диск ISO 9660),
собранный командой:

```sh
make iso
```

**Не просто копируйте файл `.iso` на USB-накопитель** (перетаскиванием /
Ctrl+C-Ctrl+V) — это только положит копию файла на флешку, но не
сделает флешку загрузочной. Вместо этого запишите его инструментом
записи сырого образа:

- **Windows:** [Rufus](https://rufus.ie) — выберите накопитель,
  выберите `hentros.iso`, схема разделов **GPT**, целевая система
  **UEFI (non-CSM)**, и если спросит, режим записи **DD Image** (не
  режим ISO). Либо [balenaEtcher](https://etcher.balena.io), который
  делает это автоматически.
- **Linux/macOS:** `dd if=hentros.iso of=/dev/sdX bs=4M status=progress`
  (**внимательно проверьте имя устройства** — это перезапишет весь
  накопитель).

Он также напрямую работает как виртуальный CD/DVD в виртуальной машине
с поддержкой UEFI (VirtualBox, VMware, QEMU: `qemu-system-x86_64 -bios
OVMF.fd -cdrom hentros.iso`). В любом случае вы попадёте в то же самое
загрузочное меню, и сначала в настройках прошивки нужно **отключить
Secure Boot** — этот загрузчик не подписан.

## Сборка

Требуется `clang`+`lld` (собранные для цели `x86_64-unknown-windows` /
PE-COFF, чтобы получалось EFI-приложение). На Debian/Ubuntu:

```sh
apt-get install clang lld qemu-system-x86 ovmf mtools dosfstools xorriso
make        # собирает iso/EFI/BOOT/BOOTX64.EFI
make iso    # также собирает hentros.iso
```

## Запуск

```sh
make run
```

загружает директорию `iso/` напрямую как FAT-том в QEMU с прошивкой
OVMF, плюс эмулирует USB мышь/клавиатуру, чтобы задействовался
настоящий путь ввода, а не PS/2-устройства QEMU по умолчанию. Двигайте
мышь, чтобы взаимодействовать с рабочим столом: щёлкните **Start**,
чтобы открыть меню, перетащите заголовок окна, чтобы подвинуть его,
щёлкните по красному **X**, чтобы закрыть его — либо используйте
стрелки и Enter, если указывающее устройство недоступно.
